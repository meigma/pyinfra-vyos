Naming: research names are plural (Ansible heritage); this package follows pyinfra's one-resource-per-call idiom — singular ops satisfying O4. `system_basics` manages one scope (system identity), not a collection. Parameter names checked against O2: `hostname`, `interface`, `destination`, `group`, `chain`, `user`, `rules`, `save` — no collisions with pyinfra global arguments; the existing meta-test extends to the new ops automatically.

## 3. Layering: typed ops are pure renderers

**Decision (D6)**: every typed op is a renderer — desired keyword model → `list[Scope]` — over the shipped diff/session machinery. No typed op gets its own session logic, script builder, or on-device read. Grounding: session-002 evidence that the session skeleton generalized with zero appliance surprises for the generic op, and the fact that all wave-2 domains are pure config-tree state (no op-mode reads, no generated artifacts). This grounds substrate *reuse*; it does not certify any typed path's device schema (§6).

**Scope algebra (D8, redesigned)**: a `Scope` is `(path: list[str], intent, sensitive: bool = False)`. `_plan_scopes` returns `list[PlannedCommand]`, where `PlannedCommand` carries `argv: list[str]` and `sensitive: bool`. Every set or delete produced from a scope inherits that scope's sensitivity. The `user` renderer marks the `authentication encrypted-password` Exact scope sensitive, so both deletion of an active old hash and setting of a new hash suppress device-authored command output. `build_commands_script` consumes `PlannedCommand`; no layer re-derives sensitivity by inspecting argv text. The intent is one of:

- **`Absent`** — ensure the node at `path` does not exist (renders a delete when active).
- **`Exact(node)`** — the node at `path` becomes exactly `node`, where `node` is a normalized leaf (`list[str]`, compared as an unordered set) or a subtree (`dict`, diffed with replace semantics: extra active keys/values pruned).
- **`Merge(subtree)`** — open-body merge at `path`: sets only, omitted state unmanaged (the shipped merge semantics).

**Disjointness invariant** (unit-tested per renderer): no two scopes emitted by one op call may own the same config node. Concretely: (a) `Exact`/`Absent` paths are pairwise non-prefix; (b) at most one `Merge` scope per owned resource, at the resource root, and its top-level keys must be disjoint from the next path token of every `Exact`/`Absent` scope beneath it — enforced by the D10 typed-key collision rejection, which refuses `values` keys that collide with a typed field. A `Merge` scope only touches keys it names, so path nesting between the merge root and exact child scopes is not ownership overlap.

This algebra replaces the draft-v1 `fields` diff mode. The underlying necessity stands — `select_subtree` returned `{}` at a leaf, so leaf state was invisible — but the fix is generalizing selection and the diff root to `Node | None` (§2), after which per-field ownership is expressed as disjoint `Exact` scopes at the exact leaf/child paths (`system host-name`, `… ethernet eth0 address`, `… authentication encrypted-password`), and absence (`disabled=False` → `Absent` at `…/disable`) is a normal node intent rather than a special delete-scope convention.

**Renderer contract**: renderers never see pyinfra state; `operations.py` feeds them arguments plus the schema key (§6) and feeds their scopes to `_plan_scopes` (A1/A2 intact). Renderers coerce ergonomic ints to `str` before token validation; everything else follows the shipped values convention (`str` / `list[str]` / `dict`, `{}` valueless).

**Intra-session ordering is not a connectivity concern**: `set`/`delete` touch only the candidate; changes take effect at the single commit. Research's "set new before deleting old" guidance (R§5) targets multi-commit tools. Cross-*op* ordering is a real concern — §7.

**Rejected alternatives**: (1) typed ops calling the public `config` op — each typed op needs multiple scopes in one commit; nesting operations would multiply sessions and entangle op semantics. (2) A parent-level `fields` diff mode — round-1 review showed it cannot coexist with the merge pass-through and child scopes under a non-overlap invariant; the exact-node algebra is both smaller and sound. (3) Closed fully-typed per-domain models — the rolling-Terraform-provider maintenance trap (R§3, R§7). Instead (**D10**) models are **shallow-typed + open-body**: identity, ownership boundaries, secrets, and safety are typed; leaf grammar passes through the shipped values convention and is validated by device commit (extends wave-1 D5). Resource-object ops accept a `values` pass-through; renderers reject `values` keys that collide with a typed field (`OperationValueError` at planning, per O3).

## 4. Per-operation surface

Common to all typed ops:

- `save: bool = False` with D13 semantics (§7); honest two-layer idempotency (controller diff → `host.noop(...)` labelled with resource identity only, never values; device `sessionChanged` remains the authority; canonicalization mismatch degrades to a truthful noop sentinel with the delta re-emitted each run, as documented on `config`).
- Wave-1 concurrency precondition (caller-serialized mutations per host, D4); token rules C2 on every rendered token; commands travel in the 0600 uploaded script, never argv (C3).
- **Uniform argument semantics**: all schema-independent argument validation runs before fact reads. The operation then reads Version, performs schema-dependent renderer validation, and only after rendering succeeds reads Configuration. Thus no desired-state error is deferred to the target, and an expensive secret-bearing Configuration read never precedes successful validation. `present=False` requires every desired-state argument (`values` included) to be unset — violations are planning errors on every op. Whole-object ops treat the desired body as **total**: an omitted optional field means desired-absent, never unmanaged. Per-field ops treat `None` as unmanaged. Each op's table row states which model it uses.

| Op | Signature (keyword-only after keys) | Owned path(s) / model | Scope rendering and omitted/`None`/empty semantics |
|---|---|---|---|
| `system_basics` | `(*, hostname=None, domain_name=None, name_servers=None, search_domains=None, time_zone=None, save=False)` | `system` identity leaves / **per-field** | One `Exact` leaf scope per provided kwarg (`host-name`, `domain-name`, `name-server`, `domain-search`, `time-zone`); `None` = unmanaged; `name_servers=[]` / `search_domains=[]` = own-and-empty (`Absent` at the leaf). All-`None` is an error. Scalar-field removal is out of model — `config(path=…, present=False)` is the documented escape hatch. Multi-value ordering unmanaged (set-equality). No secrets. |
| `interface` | `(interface, *, interface_type, addresses=None, description=None, mtu=None, disabled=None, values=None, present=True, save=False)` | `interfaces <type> <interface>` / **per-field** | `Exact` scopes at `address` (exact set), `description`, `mtu`; `disabled` tri-state (`True` → `Exact({})` at `disable`, `False` → `Absent` at `disable`, `None` unmanaged); `values` → `Merge` at the interface path (typed-key collision rejected); all typed args `None` + no `values` → `Merge({})` (ensure bare node). `present=False` → single `Absent` at the interface path; typed args must be unset. `interface_type ∈ {ethernet, loopback, dummy}` — chosen as the non-composite types with no cross-references (R§5), **not** hardware-verified until the appliance tier runs. Static groups only. Deleting a referenced group fails at device commit — commit output is the diagnostic. |
| `firewall_ruleset` | `(af, chain, *, default_action=None, description=None, rules=None, replace_rules=False, values=None, present=True, save=False)` | `firewall <af> <*chain>`, `af ∈ {ipv4, ipv6}`, `chain` a token list (`["name", "WAN_IN"]`, `["input", "filter"]`) / **per-field + per-rule** | `default_action`/`description`: `Exact` leaf scopes, `None` = unmanaged. `rules: dict[int|str, dict|None]`: with `replace_rules=False`, one `Exact` subtree scope per rule number (`{n: None}` → `Absent` at rule *n*; each rule body is total — whole-rule replace, R§1.1/R§5 keying); unlisted rules unmanaged. `replace_rules=True` → one `Exact` scope at the `rule` node: the chain's rule set becomes exactly `rules` (explicit destructive, Ansible-`overridden` analog, R§1.8); requires `rules` (may be `{}` = prune all rules); `None` entries rejected. `values` → `Merge` at the chain path (keys `default-action`, `description`, `rule` rejected). ## 5. Facts strategy

**Decision (D7)**: wave-2 ops consume the existing full-tree `Configuration` fact; no scoped facts and no typed convenience facts this wave. New this wave: `PendingSave` (§2) for `config_save`, and `pyinfra.facts.server.User` consumed (not defined) by the `user` deletion guard (§8).

- *For* the full tree: one command, one parse; the shipped `config` already requires it; its secret boundary is stated (wave-1 §3) and typed ops add no new exposure class.
- *Against scoped facts now*: `cli-shell-api returnActiveValues`/`listActiveNodes` output is shell-style quoted text with unescaped apostrophes — established unsafe to parse (R§1 pitfall 1); per-scope facts multiply SSH round trips; a second read path is surface without demand. Typed read-only facts (`Interfaces`, …) are caller sugar; deferred on the same grounds.
- *Deferral trigger, named*: scoped facts return when a deploy profile shows `Configuration` fetch dominating run time, or an appliance where the JSON tree is too large.

**Cost and coherence model (replaces draft-v1 §5.1)**: the pinned pyinfra (3.10.0; range `>=3.9.2,<4`) has **no fact cache** — `Host.get_fact` calls straight through to `api.facts.get_fact`, which runs the fact command every time (the `host.py` docstring mentioning a cache is stale). pyinfra evaluates each operation's command generator twice: once at prepare for change detection and again immediately before that operation executes. Consequently each typed-op call fetches `Configuration` (and `Version`, §6) once per evaluation — normally twice per run — and **execute-time planning always sees post-prior-operation state**. Cross-op coherence within a deploy is automatic; no invalidation machinery, no one-run-drift caveat, no one-owner-per-path deploy restriction. The doubled fetch is the accepted price; it is also the profiling signal for the scoped-facts trigger above. Implementation checklist item: verify the 3.9.x floor shares the cache-free `get_fact`; if any supported version caches facts, raise the floor rather than depending on private state (§10, §12).

## 6. Version dispatch (1.4 Sagitta vs 1.5 Circinus)

**Decision (D9, revised)**: wave 2 ships a **thin version gate and schema-key seam**, per the research's explicit conclusion that "a `Version` fact is mandatory, and typed facts/operations must select a 1.4 or 1.5 schema rather than assume that the stable session machinery implies a stable configuration tree" (R§2).

- **Mechanism**: `operations.py` fetches the `Version` fact (fact consumption is op-layer; A2 keeps it out of `_render`) and calls the pure `schema_key(version_string) -> "1.4" | "1.5"` in `_render.py`. `1.4.*` maps to `"1.4"`; `1.5.*` maps to `"1.5"`; rolling identifiers map only when explicitly qualified by fixtures and the appliance tier (initially `2026.03.*`, mapped to `"1.5"`). Bare Stream labels and later rolling releases fail closed until qualified. This is deliberate compatibility gating, not a claim that all future rolling schemas remain 1.5-compatible. Anything unrecognizable or unqualified → `OperationValueError` naming the version string and pointing at the version-agnostic `config`/`config_load` escape hatches. `config` and `config_load` remain ungated (wave-1 D5).
- **Renderers take the schema key** and select their tables by it, even though every wave-2 table is currently identical under both keys: the structural paths these ops emit — `system` identity leaves, `interfaces ethernet/loopback/dummy`, `protocols static route[6]`, `firewall group`, the modern 1.4+ `firewall <af>` chain model, `system login user` — are the Ansible-6.0 modern-baseline layouts for both target releases (R§2), and the drift R§2 enumerates (DHCP ISC→Kea, syslog child names, NTP `ptp`) lives in deferred domains. The seam therefore costs a parameter today and prevents a signature break when `dhcp_server`/`syslog` land with genuinely forked tables (the §2 trigger for splitting `_render.py`).
- **Two claims kept distinct**: (a) *caller pass-through* — 1.5-only leaves and chains ride through `values`/open chain tokens and are validated by device commit, the correct authority (extends D5); (b) *library-emitted grammar* — every typed path and table leaf the library itself emits is asserted release-compatible per the R§2 baseline, and this assertion is **fixture-checked in unit tests and verified on the appliance tier**, not "hardware-verified" today. Session-002 hardware evidence covers the generic op only.
- **Cost**: one extra cheap fact fetch (`show version`) per typed-op generator evaluation (§5 cost model).

## 7. Save/commit and session uniformity

All typed ops share the session contract via `session_run_sequence` + `build_commands_script`:

- One configure session, one commit per op call. All commands of a call are **co-staged and presented to a single commit**, so dependent fields within a scope (a rule's required leaves, a route's next-hop set) validate together (R§1.1's complete-block requirement within an op).
- **What one commit does *not* guarantee (D12 clarified)**: rollback atomicity is unproven. The 1.5 API documentation warns that mixed-component command lists may partially commit (R open question 7); the EXIT trap tears down remaining *candidate* state and is **not** rollback of active state a partially-applied commit already changed. The appliance tier adds a rejected multi-command commit probe (§11) to observe partial-application behavior on the lab release — one data point, not a cross-version guarantee. Docstrings for `interface`, `static_route`, `firewall_ruleset` (base chains), and `user` deletion state the out-of-band recovery assumption (console/OOB access) for the lockout classes.
- **Commit is immediate**: a commit changes running interfaces/routes/firewall/users the moment it succeeds and can sever the controller's SSH session before anything else runs. `save=False` limits **reboot persistence only**; it is not a dry run and not protection against immediate lockout.
- **Save gating (D13, new)**: `build_commands_script`'s save block executes only when `did_commit == 1` — aligning the script with the contract `config` already documents ("save=True persists only when this run commits"). This closes the shipped gap where a canonicalization-degraded run (commands sent, candidate unchanged, no commit) could still persist pre-existing unsaved active state. `build_load_script` keeps its unconditional idempotent save: `config_load` documents save-only runs as a supported behavior and always executes. Both behaviors are unit-tested separately.
- **Verify-then-persist, now executable**: the recommended workflow for risky changes is `op(..., save=False)` → verify reachability/facts → `config_save()`. The final step is a real operation that noops honestly (`PendingSave` `False`), fails closed when saved-state cannot be established (`PendingSave` `None` → `OperationValueError`), and saves idempotently otherwise. Save is device-global: it writes the complete active configuration to `/config/config.boot`, including unrelated active changes that were already unsaved or arrived from another controller. The caller must serialize or otherwise account for those changes; typed ownership does not scope persistence. The draft-v1 guidance to "call again with `save=True`" is withdrawn — a second identical typed call noops at the controller and cannot save. (`config_load`'s own docstring workflow still works because it always executes; unchanged.)
- **Cross-op atomicity is out of scope (D12)**: each typed op call is its own commit. Dependent resources across ops (a ruleset referencing a group) rely on pyinfra's per-host op ordering; mis-ordering fails at device commit with the device's message. When a caller needs cross-domain state in one commit, `config` with a broader owned path is the designed escape hatch. A batching construct is deferred pending demand; it would be a new contract, not a refactor.

## 8. Secrets: the `user` op

Consistent with the wave-1 boundary (secrets off argv per C3, `Configuration` declared secret-bearing):

**Decision (D11, revised)**:
- `encrypted_password` accepts **pre-hashed crypt strings only** (must start with `$`, or be the `!`/`*` lock markers); anything else — in particular plaintext — is rejected at planning with an error that names the field and accepted forms but never echoes the value. No `plaintext_password`, no `on_create` mode: VyOS would hash plaintext device-side, making it non-comparable and the op dishonestly non-idempotent (R§5). Callers hash controller-side (`mkpasswd`, passlib), keeping plaintext out of this library entirely.
- Hash comparison is a plain string diff against the active tree (`Exact` leaf scope) — idempotent because crypt hashes are stable text. The hash reaches controller memory via the `Configuration` fact (the already-stated wave-1 exposure) and travels inside the 0600 session script (C3).
- **Diagnostics, honestly stated**: the renderer marks the `authentication encrypted-password` Exact scope **sensitive** (§3); every planned command derived from it — deletion of an active old hash and setting of a new hash alike — inherits the marker, and on failure `build_commands_script` emits the ordinal/verb line and a fixed "device output suppressed (sensitive command)" notice instead of the captured device output — device error text for a bad hash is not proven hash-free, so it is not forwarded. **Commit** failure output remains forwarded for all ops: it is the primary diagnostic and suppressing it whenever a session contains a sensitive command would gut diagnosability; it is documented as potentially secret-bearing, within the wave-1 admission that controller logs handling configuration are sensitive. `host.noop`/error labels carry the username only.
- **Deletion guard**: `present=False` fetches `pyinfra.facts.server.User`, which reports the remote command environment's `$USER` through pyinfra's public `User` fact. Empty output fails closed. The guard assumes that connector privilege transformation or environment customization has not made `$USER` misleading; it is a guard against the common self-deletion case, not an authenticated connector-identity proof. If the reported identity equals the target user → planning error; if it is empty/undeterminable, the fail-closed refusal states the connected identity could not be established and names the `config` escape hatch. Documented limits: the guard does not detect the last privileged local administrator (not reliably knowable from the tree) and does not model remote-auth identities (R§5 distinguishes local from remote-auth users); `config` is the deliberate override for both.

## 9. Key decisions

- **D6 — typed ops are pure renderers over the shipped substrate**: desired model → validated disjoint `Scope` list → shared planner + session tail; no per-op session or diff code. Substrate reuse grounded in session-002; schema claims handled separately (D9).
- **D7 — one full-tree `Configuration` fact; no scoped facts; cache-free cost model**: pinned pyinfra fetches facts per generator evaluation (prepare + execute), so execute-time planning sees post-prior-op state and cross-op coherence is automatic; no invalidation machinery. Scoped facts return on a measured cost trigger.
- **D8 — exact-node scope algebra with a sensitivity carrier**: `Absent` / `Exact(leaf|subtree)` / `Merge` intents at exact paths, each scope carrying `sensitive: bool` inherited by every `PlannedCommand` derived from it; `select_subtree`/`diff_tree` root generalized to `Node | None`; disjointness invariant enforced by non-prefix exact paths plus typed-key collision rejection for the single merge scope. Replaces the unsound parent-level `fields` mode.
- **D9 — thin version gate + schema-key seam**: `Version` consumed in the op layer, pure `schema_key()` mapping (stable families whitelisted; rolling identifiers only when fixture/appliance-qualified; unknown → fail closed, `config` escape hatch), renderer tables keyed by schema even while identical; per R§2's mandatory-Version conclusion. Library-emitted grammar is fixture- and appliance-verified, not assumed.
- **D10 — shallow-typed + open-body models**: identity, ownership, secrets, safety typed; leaf grammar passed through and device-validated; `values` pass-through with typed-key collision rejection; rejected the closed-full-schema alternative as the rolling-provider maintenance trap (R§3, R§7).
- **D11 — `user` secrets: encrypted-hash-only; sensitive-scope output suppression carried through `PlannedCommand`; forwarded commit output documented as residual exposure; remote-identity deletion guard failing closed.**
- **D12 — one commit per op call; cross-op atomicity out of scope; rollback atomicity explicitly unproven**: co-staged single-commit validation is the claimed guarantee; teardown is not rollback; lockout classes carry an out-of-band recovery assumption.
- **D13 — commit-gated save for command scripts + `config_save` persist phase**: `build_commands_script` saves only when this script committed; `config_load` save semantics unchanged; `config_save` (with the tri-state `PendingSave`, failing closed on unknown state) makes verify-then-persist executable; persistence is device-global, not scoped by typed ownership.

## 10. Risks

| Risk | Handling |
|---|---|
| pyinfra floor (3.9.x) might cache facts, breaking the §5 coherence model | Implementation verifies `get_fact` on the floor version; if any supported release caches, raise the dependency floor (L2) — never reach into private state. |
| Device canonicalization of typed values (address forms, quoted descriptions, hash whitespace) | Same degradation as shipped `config`: truthful device-noop sentinel + perpetual controller delta re-emission. Appliance tier catches each op's hotspots; learned canonical forms go in docstrings, not normalization code. |
| Lockout: management-interface address replace, base-chain `default_action`, user deletion, route changes | `user` has the fail-closed identity guard; the others carry the §7 verify-then-`config_save` workflow and the documented out-of-band recovery assumption. Commit-confirm remains deferred (R§1: hard; prompt/EOF and reload-vs-reboot contradictions). |
| Partial application on a rejected multi-command commit | Unproven either way (R open question 7). Appliance failure-scenario probe (§11) documents observed behavior on the lab release; docstrings do not claim rollback. |
| Cross-op dependency mis-ordering (rule → missing group) | Out of contract by D12; device commit error is the diagnostic; docstrings state the ordering obligation. |
| Open-body typos create wrong-but-valid nodes | Config-mode `set` validates against the device's path templates; invalid paths fail at `set` with ordinal diagnostic. Valid-but-unintended paths are the caller's model, as with `config` today. |
| Multi-value ordering unmanaged (set-equality) | Carried from session-002 deliberately; revisit if an order-significant node bites in a typed domain. |
| `firewall_ruleset` `replace_rules=True` removing management access | Explicit opt-in flag; destructive semantics in the docstring (Ansible `overridden` precedent, R§1.8). |
| Doubled fact fetches (prepare + execute, no cache) slow large deploys | Accepted cost of planning against reality; it is exactly the profiling trigger for the scoped-facts deferral (§5). |
| Seven-op wave overruns a session | Ops are independently shippable; cut order if needed: `config_save` + access path first (`system_basics`, `interface`, `static_route`, `user`), firewall pair second. |

## Appendix B — Round-2 review amendments

Round 2 (final; verdict accept-with-notes) closed the review: the round-1 blockers were judged substantially resolved and the remaining findings were issued as self-contained amendments to apply without further review. All are applied verbatim above; none rebutted:

1. **A1 (High) — sensitivity carrier.** `Scope` gains `sensitive: bool = False`; `_plan_scopes` returns `PlannedCommand(argv, sensitive)`; every set or delete derived from a scope inherits its sensitivity — covering both deletion of an active old password hash and setting of a new one; `build_commands_script` consumes `PlannedCommand` and no layer re-derives sensitivity from argv text (§2, §3, §8, D8/D11).
2. **A2 (High) — firewall contracts repaired.** `firewall_group` regains `members=None` with conditional requiredness (required when `present=True`, `[]` = own-and-empty; both `members` and `description` must be `None` when `present=False`); `firewall_ruleset` rejects the owns-nothing call (`present=True`, `replace_rules=False`, all desired args `None`) and rejects empty individual rule bodies before facts are read (§4).
3. **A3 (Medium) — bounded rolling dispatch.** `schema_key` maps only whitelisted stable families plus explicitly qualified rolling identifiers (initially `2026.03.*` → "1.5"); bare Stream labels and later rolling releases fail closed until fixture/appliance-qualified; "forward-compatible on newer streams" withdrawn (§6, D9). Supersedes the broader rolling/stream mapping recorded in appendix A item 4.
4. **A4 (Medium) — typed `@local` test precondition.** Typed-op prepare/assembly tests provide a deterministic `vbash` fixture on `PATH` returning a supported Version and empty configuration, so they pass the fail-closed Version gate through the real pyinfra pipeline; unknown/default-Version rejection is a separate test; substrate tests keep exercising the no-`vbash` defaults (§11).
5. **A5 (Medium) — fail-closed save state, global persistence, honest identity guard.** `PendingSave` is tri-state (`FactBase[bool | None]`, default `None`); `config_save` raises `OperationValueError` on `None` rather than reporting a clean noop; save is documented as device-global persistence not scoped by typed ownership (§2, §4, §7, D13). The `user` deletion-guard wording is downgraded to honest `$USER` semantics — a common-case self-deletion guard, not an authenticated connector-identity proof (§8).
6. **A6 (Low) — route body and validation order.** Static-route bodies normalize under the `next-hop` wrapper (`{"next-hop": {address: {}}}` / `{"next-hop": {address: per_hop_subtree}}`), making `values["next-hop"]` a typed-key collision; the validation claim is restated as the realistic two-stage order: schema-independent validation → Version read + schema-dependent renderer validation → Configuration read + planning (§2, §4).
