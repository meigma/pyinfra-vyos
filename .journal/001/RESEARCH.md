"# Research report: recommended facts and operations for `pyinfra-vyos`\n\n## Executive synthesis\n\n**Recommendation.** Build the package around one SSH-native configuration substrate, then add a deliberately small typed surface. The strongest cross-ecosystem signal is a generic, scoped configuration-tree operation backed by active-configuration facts: Ansible’s `vyos_config` is set/delete plus line diff; the community Terraform providers primarily expose path/block/tree resources; the VyOS API is path-oriented (`showConfig`, `returnValues`, `exists`, `set`, `delete`); and NAPALM’s VyOS driver exposes SSH merge/compare/commit/discard. Typed demand is strongest for interfaces, static routes, firewall, routing policy/protocols, NTP/logging, and users. [Ansible collection index](https://docs.ansible.com/projects/ansible/latest/collections/vyos/vyos/index.html), [Ansible config](https://docs.ansible.com/projects/ansible/latest/collections/vyos/vyos/vyos_config_module.html), [Foltik resources](https://github.com/Foltik/terraform-provider-vyos/tree/main/docs/resources), [VyOS 1.5 API](https://docs.vyos.io/en/1.5/automation/vyos-api.html), [NAPALM driver](https://github.com/napalm-automation-community/napalm-vyos/blob/develop/napalm_vyos/vyos.py#L116-L225).\n\nThis is a **demand inference**, not usage telemetry: module/provider breadth proves that maintainers and users have invested in those surfaces, but no reliable adoption statistics were found.\n\n## 1. SSH scripting primer and hard constraints\n\n### Supported public mechanism\n\nBoth VyOS 1.4 Sagitta and 1.5 Circinus document the same non-interactive pattern:\n\n```bash\nssh ROUTER 'vbash -s' <<'EOF'\nsource /opt/vyatta/etc/functions/script-template\nconfigure\nset ...\ndelete ...\ncommit\nsave\nexit\nEOF\n```\n\nOperational commands in such a script must be prefixed with `run`. The documented remote entry point is `/bin/vbash -s`, and the command DSL comes from `/opt/vyatta/etc/functions/script-template`. [1.4 command scripting](https://docs.vyos.io/en/1.4/automation/command-scripting.html), [1.5 command scripting](https://docs.vyos.io/en/1.5/automation/command-scripting.html).\n\nVyOS distinguishes **working**, **active/running**, and **saved** configuration. `set`/`delete` change the working candidate, `commit` makes it active, and `save` separately persists it, normally to `/config/config.boot`. [1.4 CLI terminology](https://docs.vyos.io/en/1.4/cli.html#terminology), [1.5 CLI editing](https://docs.vyos.io/en/1.5/cli.html#editing-the-configuration).\n\n### `cli-shell-api`\n\nCurrent Sagitta and Circinus source branches expose the same relevant read methods:\n\n- candidate/working: `exists`, `listNodes`, `returnValue`, `returnValues`;\n- active/running: `existsActive`, `listActiveNodes`, `returnActiveValue`, `returnActiveValues`;\n- effective/commit-processing view: corresponding `*Effective` methods;\n- session lifecycle: `getSessionEnv`, `setupSession`, `inSession`, `teardownSession`;\n- rendering: `showCfg` and `showConfig`.\n\nBoolean queries return exit status 0 for true and nonzero for false; paths are separate argv components. [Sagitta source](https://github.com/vyos/vyatta-cfg/blob/sagitta/src/cli_shell_api.cpp#L213-L451), [Circinus source](https://github.com/vyos/vyatta-cfg/blob/circinus/src/cli_shell_api.cpp#L213-L451).\n\nA configuration session is created by evaluating `cli-shell-api getSessionEnv $PPID`, then calling `setupSession`; it must be torn down. The sourced `configure` helper performs that sequence. [Sagitta script-template](https://github.com/vyos/vyatta-cfg/blob/sagitta/functions/wrapper/script-template#L55-L96), [Circinus script-template](https://github.com/vyos/vyatta-cfg/blob/circinus/functions/wrapper/script-template#L55-L96).\n\n`showConfig` supports active-only, working-only, defaults, secret hiding, context diff, commands, and explicit config-file selectors. Outside a session, facts must request `--show-active-only`; bare `showConfig` defaults to active-versus-working and can abort because `@WORKING` requires a session. [option implementation](https://github.com/vyos/vyatta-cfg/blob/sagitta/src/cli_shell_api.cpp#L494-L545), [lower implementation](https://github.com/vyos/vyatta-cfg/blob/sagitta/src/cnode/cnode-algorithm.cpp#L923-L960).\n\nTwo important API pitfalls are established in current source:\n\n1. `list*`/`returnValues*` output is shell-style single-quoted text, not JSON, and embedded apostrophes are not escaped. It must not be blindly `eval`ed. [printer](https://github.com/vyos/vyatta-cfg/blob/sagitta/src/cli_shell_api.cpp#L45-L52).\n2. `--show-ignore-edit` also clears a requested subtree path in the current lower implementation. It is suitable for a root dump, not a scoped read. [Sagitta source](https://github.com/vyos/vyatta-cfg/blob/sagitta/src/cnode/cnode-algorithm.cpp#L932-L948), [Circinus source](https://github.com/vyos/vyatta-cfg/blob/circinus/src/cnode/cnode-algorithm.cpp#L923-L948).\n\nThe only prose method reference located is a deleted, 2020-era page describing Vyatta 6.4, so current branch source is the stronger authority for method behavior. [archived reference](https://vyos.dev/w/development/cli-shell-api/).\n\n### Hard constraints imposed on this plugin\n\n1. **One diff, one SSH shell, one configuration session, one commit.** Session environment does not survive separate pyinfra SSH commands. Dependent fields must be staged before commit; VyOS explicitly calls out DHCP, PPPoE, IPsec, VXLAN, other tunnels, NAT rules, and firewall rules as requiring complete blocks at validation time. [script-template](https://github.com/vyos/vyatta-cfg/blob/sagitta/functions/wrapper/script-template#L55-L96), [1.5 API atomic-block discussion](https://docs.vyos.io/en/1.5/automation/vyos-api.html#configure).\n2. **Use effective group `vyattacfg`, not a root-owned configuration script.** Both manuals warn that running a configuration-changing script with `sudo` can make subsequent manual `set` fail until reboot; they prescribe `sg vyattacfg`. Local VyOS users are provisioned with `/bin/vbash` and `vyattacfg`, but remote-auth users should be preflighted rather than assumed equivalent. [1.4 warning](https://docs.vyos.io/en/1.4/automation/command-scripting.html#executing-configuration-scripts), [1.5 warning](https://docs.vyos.io/en/1.5/automation/command-scripting.html#execute-configuration-scripts), [Circinus local-user source](https://github.com/vyos/vyos-1x/blob/circinus/src/conf_mode/system_login.py#L291-L312).\n3. **Read active state explicitly.** Facts should use `show configuration json`, `show configuration commands`, `*Active` methods, or `showConfig --show-active-only`, not candidate/effective methods by accident. [CLI configuration JSON](https://docs.vyos.io/en/1.5/cli.html#opcmd-show-configuration-json), [active API source](https://github.com/vyos/vyatta-cfg/blob/sagitta/src/cli_shell_api.cpp#L213-L451).\n4. **Commit and save are separate policy decisions.** A no-op yields nothing; a changed operation commits once and saves only if persistence is requested. The HTTP API and Terraform providers expose this distinction, while NAPALM’s driver immediately saves after commit, so external tools do not establish one universal default. [1.5 API](https://docs.vyos.io/en/1.5/automation/vyos-api.html#configure), [Foltik provider](https://github.com/Foltik/terraform-provider-vyos/blob/main/docs/index.md), [NAPALM source](https://github.com/napalm-automation-community/napalm-vyos/blob/develop/napalm_vyos/vyos.py#L199-L211).\n5. **Treat configuration output as secret-bearing.** The documented JSON example includes a password hash and SSH key data; `show configuration commands` only hides private data when `strip-private` is requested, and `showConfig` only hides it with `--show-hide-secrets`. [1.5 CLI](https://docs.vyos.io/en/1.5/cli.html#seeing-and-navigating-the-configuration), [showConfig options](https://github.com/vyos/vyatta-cfg/blob/sagitta/src/cli_shell_api.cpp#L494-L545).\n6. **Do not infer shell success from the public aliases alone.** Current wrapper functions can mask the child return code after `my_commit`, `my_set`, or save by running later successful helper commands. A load-bearing operation needs either checked lower-level commands inside the session or a verified postcondition. [commit wrapper](https://github.com/vyos/vyatta-cfg/blob/sagitta/functions/interpreter/vyatta-cfg-run#L101-L130), [generic wrapper](https://github.com/vyos/vyatta-cfg/blob/sagitta/functions/interpreter/vyatta-cfg-run#L341-L360), [save wrapper](https://github.com/vyos/vyatta-cfg/blob/sagitta/functions/interpreter/vyatta-cfg-run#L168-L183).\n7. **Serialize configuration mutations per host.** Current sources expose session IDs and a shared commit path but no documented conflict/locking contract safe enough to promise concurrent mutations. This is a conservative inference from the session model. [session operation table](https://github.com/vyos/vyatta-cfg/blob/sagitta/src/cli_shell_api.cpp#L638-L658).\n8. **Subtree ownership must be explicit.** Terraform’s broad generated provider needs parent/child bindings and warns about destructive child deletion; Ansible warns that `overridden` can remove management access. Omitted state should mean unmanaged unless the operation explicitly owns/replaces a subtree. [rolling provider](https://github.com/echowings/terraform-provider-vyos-rolling/blob/main/docs/index.md), [Ansible resource-state semantics](https://docs.ansible.com/projects/ansible/latest/network/user_guide/network_resource_modules.html).\n\n### Commit-confirm\n\nThe public CLI supports `commit-confirm [minutes]` followed by `confirm`; the documented default timeout is 10 minutes. Documentation says expiry can reload the last completed configuration or reboot to saved configuration. [1.4 CLI](https://docs.vyos.io/en/1.4/cli.html#cfgcmd-commit-confirm-minutes), [1.5 CLI](https://docs.vyos.io/en/1.5/cli.html#cfgcmd-commit-confirm-minutes).\n\nIt is **hard**, not a normal first-wave flag:\n\n- the public wrapper prompts and can loop on EOF in `vbash -s`;\n- current internal `config-mgmt commit_confirm -t ... -y` has a no-prompt mode, but it is not documented as a public automation API;\n- confirmation must occur only after an independent connectivity check;\n- the protected candidate must not be saved before confirmation;\n- a commit failure after the timer is created can leave a timer pending. [wrapper](https://github.com/vyos/vyatta-cfg/blob/sagitta/functions/interpreter/vyatta-cfg-run#L132-L164), [no-prompt source](https://github.com/vyos/vyos-1x/blob/sagitta/python/vyos/config_mgmt.py#L692-L750), [EOF behavior](https://github.com/vyos/vyos-1x/blob/sagitta/python/vyos/utils/io.py#L47-L66).\n\nThere is also a contradiction: both manuals advertise `action reload|reboot`, but current branch-tip `config_mgmt.py` appears always to execute the reboot revert path. This needs appliance-version validation before promising reload behavior. [documented behavior](https://docs.vyos.io/en/1.5/cli.html#cfgcmd-commit-confirm-minutes), [Sagitta implementation](https://github.com/vyos/vyos-1x/blob/sagitta/python/vyos/config_mgmt.py#L166-L238), [Circinus implementation](https://github.com/vyos/vyos-1x/blob/circinus/python/vyos/config_mgmt.py#L166-L238).\n\n## 2. Version findings: 1.4 versus 1.5\n\n**Stable substrate:** no relevant behavioral difference was found between current Sagitta and Circinus branches of `cli_shell_api.cpp`, `cnode-algorithm.cpp`, or `script-template`; the documented `vbash` mechanism is also the same. [Sagitta API source](https://github.com/vyos/vyatta-cfg/blob/sagitta/src/cli_shell_api.cpp), [Circinus API source](https://github.com/vyos/vyatta-cfg/blob/circinus/src/cli_shell_api.cpp), [1.4 scripting](https://docs.vyos.io/en/1.4/automation/command-scripting.html), [1.5 scripting](https://docs.vyos.io/en/1.5/automation/command-scripting.html).\n\n**Schemas do differ materially:**\n\n- 1.4 uses ISC DHCP; 1.5 uses Kea, adds required unique `subnet-id`, and moves common options beneath `option` (for example, `domain-name` and `default-router`). [1.4 DHCP](https://docs.vyos.io/en/1.4/configuration/service/dhcp-server.html), [1.5 DHCP](https://docs.vyos.io/en/1.5/configuration/service/dhcp-server.html), [release history](https://docs.vyos.io/en/1.5/introducing/history.html#circinus-1-5).\n- Syslog child names differ: Sagitta documents `file`, `host`, and `user`; Circinus documents `local` and `remote` plus expanded TLS support. [1.4 syslog](https://docs.vyos.io/en/1.4/configuration/system/syslog.html), [1.5 syslog](https://docs.vyos.io/en/1.5/configuration/system/syslog.html).\n- Circinus adds NTP `ptp`/`interleave`, directional firewall IPsec matches, additional raw/bridge firewall surface, and `add system image latest`. [Ansible 6.0 changelog](https://raw.githubusercontent.com/ansible-collections/vyos.vyos/6.0.0/CHANGELOG.rst), [1.5 firewall](https://docs.vyos.io/en/1.5/configuration/firewall/ipv4.html), [1.5 image update](https://docs.vyos.io/en/1.5/installation/update.html).\n- Ansible’s modern 1.4+ model uses BGP `system-as`, address-family ownership, OSPF interface configuration under the protocol subtree, nftables-era firewall chains, and `service ntp`. Those are the correct baselines for both target releases, not legacy pre-1.4 layouts. [Ansible 6.0 changelog](https://raw.githubusercontent.com/ansible-collections/vyos.vyos/6.0.0/CHANGELOG.rst).\n\nTherefore a `Version` fact is mandatory, and typed facts/operations must select a 1.4 or 1.5 schema rather than assume that the stable session machinery implies a stable configuration tree.\n\n## 3. Automation integrations as operator-demand signals\n\n### Ansible `vyos.vyos` 6.0.0\n\nThe current collection has generic `command`, `config`, and `facts` modules plus typed resources for interfaces/L3/LAG, static routes, BGP global/address-family, OSPFv2/v3/interfaces, prefix lists, route maps, firewall global/rules, NTP, logging, LLDP, SNMP, hostname, and users. [module index](https://docs.ansible.com/projects/ansible/latest/collections/vyos/vyos/index.html).\n\nIts common resource states map almost perfectly to pyinfra:\n\n- `gathered` → fact;\n- `parsed` → parser contract;\n- `rendered` → desired-state command builder;\n- `merged`, `replaced`, `overridden`, `deleted` → diff/ownership scopes.\n\n[Ansible resource-state semantics](https://docs.ansible.com/projects/ansible/latest/network/user_guide/network_resource_modules.html).\n\n`vyos_config` confirms the generic substrate: exact full-form set/delete statements, active-config comparison, optional backup, and save control. Its warning that abbreviations/device-normalized syntax break idempotency applies directly to a command-stream parser. [vyos_config](https://docs.ansible.com/projects/ansible/latest/collections/vyos/vyos/vyos_config_module.html).\n\n### Terraform\n\n- Foltik’s maintained-but-WIP provider offers generic single-value, atomic block, and block-tree resources, one typed static-host mapping, a configuration data source, and save control. [repository](https://github.com/Foltik/terraform-provider-vyos), [single config](https://github.com/Foltik/terraform-provider-vyos/blob/main/docs/resources/config.md), [atomic block](https://github.com/Foltik/terraform-provider-vyos/blob/main/docs/resources/config_block.md), [block tree](https://github.com/Foltik/terraform-provider-vyos/blob/main/docs/resources/config_block_tree.md).\n- TGNThump/benjamin-pilgrim exposes one generic path plus JSON subtree resource and persistence control. [resource](https://github.com/benjamin-pilgrim/terraform-provider-vyos/blob/main/docs/resources/config.md).\n- The broad echowings rolling provider generates thousands of typed resources from rolling schemas, but is explicitly early access/rolling-specific. It demonstrates demand for typed validation while also demonstrating the maintenance cost and hierarchy hazards of mirroring every VyOS node. [provider docs](https://github.com/echowings/terraform-provider-vyos-rolling/blob/main/docs/index.md), [resources](https://github.com/echowings/terraform-provider-vyos-rolling/tree/main/docs/resources).\n\nThese are community HTTP-API providers, not official stable-version authorities. The official VyOS Terraform pages focus on instance deployment, not router configuration. [VyOS Terraform overview](https://docs.vyos.io/en/1.5/automation/terraform/terraformvyos.html).\n\n### NAPALM and Nornir\n\nOfficial VyOS docs link the community NAPALM driver but mark it **testing**. It supports SSH merge, compare, commit, discard, and structured getters including facts, interfaces/IP/counters, ARP, BGP neighbors, LLDP neighbors, NTP peers/stats, users, environment, SNMP, ping, and running/startup/candidate config. [VyOS NAPALM guide](https://docs.vyos.io/en/1.5/automation/vyos-napalm.html), [driver source](https://github.com/napalm-automation-community/napalm-vyos/blob/develop/napalm_vyos/vyos.py#L227-L958).\n\nIts parser code is only a capability signal: the published package is old and the README targets VyOS 1.1.x, not 1.4/1.5. The same README’s claim that VyOS has no HTTP API is now contradicted by current 1.4/1.5 docs. [NAPALM README](https://github.com/napalm-automation-community/napalm-vyos/blob/develop/README.md), [1.4 API](https://docs.vyos.io/en/1.4/automation/vyos-api.html), [1.5 API](https://docs.vyos.io/en/1.5/automation/vyos-api.html).\n\nNornir contributes orchestration and wraps NAPALM/Netmiko/Scrapli; it does not provide a separate typed VyOS state model. Netmiko labels VyOS limited-testing, and Scrapli’s community VyOS driver supplies prompts/failure strings but no structured parser identifiers. [Nornir plugins](https://nornir.readthedocs.io/en/latest/plugins/index.html), [Netmiko platforms](https://github.com/ktbyers/netmiko/blob/develop/PLATFORMS.md), [Scrapli VyOS driver](https://github.com/scrapli/scrapli_community/blob/main/scrapli_community/vyos/vyos/vyos.py).\n\n### HTTP API surface\n\nAlthough out of implementation scope, the official API is a strong signal of useful primitives: retrieve/show, exists/returnValues/showConfig, batched set/delete/comment, save/load/merge, generate, image add/delete, reset, reboot, poweroff, and—documented in 1.5—commit-confirm. The API explicitly requires dependent fields to be batched and warns that large/multi-component applies may time out or partially commit. [1.5 API](https://docs.vyos.io/en/1.5/automation/vyos-api.html).\n\n## 4. Prioritized candidate facts\n\n`show configuration json` is the best documented machine-readable configuration source in both releases; it represents arrays for repeated leaves and `{}` for valueless nodes, so normalization is required. `show configuration commands` is the best canonical/replay source but requires quoting-aware parsing and can expose secrets. [1.4 CLI](https://docs.vyos.io/en/1.4/cli.html#seeing-and-navigating-the-configuration), [1.5 CLI](https://docs.vyos.io/en/1.5/cli.html#seeing-and-navigating-the-configuration).\n\n| Priority | Fact name | Reads and parse source | Recommendation |\n|---|---|---|---|\n| P0 | `Version` | `show version`; parse release/version, model, serial/platform where available. Ansible’s base facts expose version/model/serial. [Ansible facts](https://docs.ansible.com/projects/ansible/latest/collections/vyos/vyos/vyos_facts_module.html) | Mandatory version gate for every typed parser/renderer. |\n| P0 | `Configuration` | Full active tree from `run show configuration json` (or non-pretty form). [1.5 CLI](https://docs.vyos.io/en/1.5/cli.html#opcmd-show-configuration-json) | Primary shared fact for typed operations; mark sensitive and never log raw output. |\n| P0 | `ConfigurationCommands` | `run show configuration commands`; optional `\\| strip-private`. Alternatively root `cli-shell-api --show-active-only --show-ignore-edit --show-commands -- showConfig`. [CLI](https://docs.vyos.io/en/1.5/cli.html#opcmd-show-configuration-commands), [source](https://github.com/vyos/vyatta-cfg/blob/sagitta/src/cli_shell_api.cpp#L494-L545) | Canonical flat representation for generic scoped diff and backup; redacted mode is not a faithful restore source. |\n| P0 | `ConfigExists(path)` | `/bin/cli-shell-api existsActive <argv...>`; rc 0/1. [source](https://github.com/vyos/vyatta-cfg/blob/sagitta/src/cli_shell_api.cpp#L213-L232) | Cheap precise probe without fetching/caching the entire secret-bearing tree. |\n| P0 | `ConfigValue(path)` / `ConfigValues(path)` | `returnActiveValue(s)` after `getNodeType`/`isMulti`. [source](https://github.com/vyos/vyatta-cfg/blob/sagitta/src/cli_shell_api.cpp#L358-L451) | Useful, but plural parsing is unsafe for arbitrary apostrophes/newlines; prefer JSON-tree selection where possible. |\n| P0 | `Interfaces` | Structured `interfaces` subtree from `Configuration`; addresses, descriptions, disabled state, MTU, VIFs, and common interface types. [VyOS Ethernet](https://docs.vyos.io/en/1.5/configuration/interfaces/ethernet.html), [Ansible interfaces/L3 modules](https://docs.ansible.com/projects/ansible/latest/collections/vyos/vyos/index.html) | Direct input for the highest-value typed operation. |\n| P0 | `StaticRoutes` | `protocols.static` subtree or canonical `show configuration commands` static-route lines. [VyOS static routes](https://docs.vyos.io/en/1.5/configuration/protocols/static.html), [Ansible static routes](https://docs.ansible.com/projects/ansible/latest/collections/vyos/vyos/vyos_static_routes_module.html) | Stable AF/prefix/next-hop keys; clean diff source. |\n| P0 | `Firewall` | `firewall` subtree, split into global/options, groups, base/custom chains, and sequence-keyed rules. [VyOS firewall groups](https://docs.vyos.io/en/1.5/configuration/firewall/groups.html), [Ansible firewall modules](https://docs.ansible.com/projects/ansible/latest/collections/vyos/vyos/index.html) | Needed before firewall operations; version-aware for 1.5-only fields. |\n| P0 | `NAT` | `nat` subtree, keyed by source/destination and rule number. [VyOS NAT44](https://docs.vyos.io/en/1.5/configuration/nat/nat44.html) | Needed before whole-rule reconciliation. |\n| P0 | `Users` | `system.login.user` subtree; expose names/full names/public keys and only explicitly requested password hashes. [VyOS login](https://docs.vyos.io/en/1.5/configuration/system/login.html), [Ansible user](https://docs.ansible.com/projects/ansible/latest/collections/vyos/vyos/vyos_user_module.html) | Default output must redact hashes/secrets; public keys are cleanly comparable. |\n| P1 | `SystemConfig` / `ServicesConfig` | Selected `system` and `service` subtrees: hostname, name servers, SSH, NTP, syslog, DNS, DHCP. [VyOS config JSON](https://docs.vyos.io/en/1.5/cli.html#opcmd-show-configuration-json) | Prefer selected structured facts over many text parsers; dispatch by version for DHCP/syslog. |\n| P1 | `CommitRevisions` | `run show system commit`; Ansible exposes commits as a fact. [VyOS CLI](https://docs.vyos.io/en/1.5/cli.html#opcmd-show-system-commit), [Ansible facts](https://docs.ansible.com/projects/ansible/latest/collections/vyos/vyos/vyos_facts_module.html) | Useful audit/rollback evidence. |\n| P1 | `SavedConfiguration` / `ConfigurationState` | Saved `/config/config.boot` rendered canonically or compared with active via explicit config selectors; do not expose raw secrets. [CLI save/load](https://docs.vyos.io/en/1.5/cli.html#saving-and-loading-manually), [showConfig selectors](https://github.com/vyos/vyatta-cfg/blob/sagitta/src/cli_shell_api.cpp#L494-L545) | Enables “active differs from boot config” and idempotent save decisions. |\n| P1 | `InterfaceStatus` / `InterfaceCounters` | `run show interfaces` and detail output; text parser. NAPALM already treats these as useful structured getters. [Ethernet operations](https://docs.vyos.io/en/1.5/configuration/interfaces/ethernet.html#operation), [NAPALM source](https://github.com/napalm-automation-community/napalm-vyos/blob/develop/napalm_vyos/vyos.py#L227-L655) | Useful operational facts, but fixture both versions; official docs do not promise JSON output. |\n| P1 | `RoutingTable` | `run show ip route` and `run show ipv6 route`; text parser. [static-route guide](https://docs.vyos.io/en/1.5/configuration/protocols/static.html) | Useful postcondition/diagnostics; not the desired-config fact. |\n| P1 | `BGPNeighbors` / `OSPFNeighbors` | `run show bgp ... summary`, `run show ip ospf neighbor`, and OSPFv3 equivalent; text parsers. [BGP operational commands](https://docs.vyos.io/en/1.5/configuration/protocols/bgp.html), [OSPF](https://docs.vyos.io/en/1.5/configuration/protocols/ospf.html) | Strong operator value, but later because output compatibility is unproven. |\n| P1 | `DHCPLeases` | Version-specific `run show dhcp server leases`/statistics text. [1.4 DHCP](https://docs.vyos.io/en/1.4/configuration/service/dhcp-server.html#operation-mode), [1.5 DHCP](https://docs.vyos.io/en/1.5/configuration/service/dhcp-server.html#operation-mode) | Useful but must fixture ISC versus Kea output. |\n| P1 | `WireGuardStatus` / `IPsecStatus` | `run show interfaces wireguard` and IPsec SA/status commands; text parser, redacted. [WireGuard](https://docs.vyos.io/en/1.5/configuration/interfaces/wireguard.html), [IPsec](https://docs.vyos.io/en/1.5/configuration/vpn/ipsec/site2site_ipsec.html) | Operational visibility only; never return private/PSK material. |\n| P1 | `Images` | `run show system image`; installed/default/running image names. Recommended first wave (8 operations)\n\n1. **`configuration`** — essential escape hatch and shared ownership/diff semantics.\n2. **`system_basics`** — hostname, resolver/search settings, and time zone; low risk and universal.\n3. **`interfaces`** — initially core Ethernet/loopback/dummy attributes and addresses; defer composite interfaces.\n4. **`static_routes`** — IPv4/IPv6, next-hop/interface, distance, blackhole/reject.\n5. **`firewall_groups`** — static address/network/port/interface groups.\n6. **`firewall_rules`** — modern 1.4+/1.5 global/base/custom rule model, with merged ownership as the safe default.\n7. **`nat_rules`** — NAT44 source/destination whole-rule ownership.\n8. **`users`** — presence and SSH public keys first; encrypted hashes optional; no implicit plaintext rotation.\n\nEvery first-wave configuration operation should use the same changed/no-op/commit/persistence behavior; `save_configuration` can be exposed as a separate helper without changing the domain count. This wave covers the central router access path, addressing, routing, policy, translation, and administrator access while avoiding the largest version/secret/lifecycle traps. The prioritization is an informed inference from the Ansible surface, generic Terraform providers, API validation model, and official domain docs cited above.\n\n## 7. Later versus skip\n\n### Next wave\n\n- `ntp`, `syslog`, `ssh_service`, `dns_forwarding`, `save_configuration`, and `config_archive`: high value, mostly bounded; syslog needs a version adapter.\n- `prefix_lists` then `route_maps`, then `bgp`/`ospf`: Ansible demonstrates demand and feasible state models, but ordering and operational disruption deserve a second wave.\n- `dhcp_server`: useful enough to support, but only after separate Sagitta ISC and Circinus Kea schemas exist.\n- `wireguard`: after secret-redaction/on-create semantics and multi-subtree route ownership are settled.\n- Runtime facts: interface counters, route table, BGP/OSPF neighbors, DHCP leases, VPN status, LLDP/ARP/NTP; fixture all text parsers on both releases.\n- Composite interface types, advanced/raw/bridge firewall, NAT66, DHCP HA/DDNS, authoritative/dynamic DNS, SNMP/LLDP config.\n\n### Later only as constrained, explicit workflows\n\n- `ipsec`: typed profiles, not arbitrary flat leaves.\n- named backup/export with an explicit secret-handling destination.\n- whole-config merge/restore with an out-of-band recovery path.\n- image install/default/delete and reboot orchestration.\n- commit-confirm after live validation of the installed point release and an independent reachability/confirm workflow.\n\n### Skip as ordinary declarative operations\n\n- `reset bgp`, `reset vpn ipsec`, daemon restarts, reboot, poweroff, ad-hoc `generate`, and factory restore. They are imperative/disruptive actions rather than durable desired state; if ever exposed, they should be unmistakably imperative. VyOS itself classifies `reset` as locally disruptive and `restart` as subsystem-disruptive. [CLI command families](https://docs.vyos.io/en/1.5/cli.html#operational-mode-command-families).\n- a bespoke operation for every generated VyOS schema node. The rolling Terraform provider demonstrates the scale and parent/child hazards; the generic scoped operation plus selective typed resources is the maintainable cut.\n- legacy pre-1.4 firewall-interface attachment. The current Ansible collection explicitly deprecates it for 1.4+. [Ansible changelog](https://raw.githubusercontent.com/ansible-collections/vyos.vyos/6.0.0/CHANGELOG.rst).\n\n## 8. Contradictions and remaining unknowns\n\n### Contradictions found\n\n- Current `cli-shell-api` source is authoritative enough to inspect, but there is no current official 1.4/1.5 prose reference; the only method table is stale/deleted Vyatta-era documentation. [archived page](https://vyos.dev/w/development/cli-shell-api/), [current source](https://github.com/vyos/vyatta-cfg/blob/sagitta/src/cli_shell_api.cpp).\n- Commit-confirm documentation offers `reload`, while current branch-tip source appears always to arm a reboot revert. Do not promise reload without appliance validation. [docs](https://docs.vyos.io/en/1.5/cli.html#cfgcmd-commit-confirm-minutes), [source](https://github.com/vyos/vyos-1x/blob/circinus/python/vyos/config_mgmt.py#L166-L238).\n- The generic CLI JSON example still shows NTP under `system`, while dedicated 1.4/1.5 references use `service ntp`; use dedicated docs and live JSON. [CLI example](https://docs.vyos.io/en/1.5/cli.html#seeing-and-navigating-the-configuration), [NTP reference](https://docs.vyos.io/en/1.5/configuration/service/ntp.html).\n- Sagitta’s “other script languages” example incorrectly uses input redirection where Circinus uses executable process substitution. [1.4 example](https://docs.vyos.io/en/1.4/automation/command-scripting.html#other-script-languages), [1.5 correction](https://docs.vyos.io/en/1.5/automation/command-scripting.html#other-script-languages).\n- Ansible docs contain parse-command defects: the BGP-global page refers to EOS output; the BGP-AF page uses singular `show configuration command`; OSPF-interface parse guidance conflicts with its own modern rendered paths. Treat module state models as signals, not parser commands to copy. [BGP global](https://docs.ansible.com/projects/ansible/latest/collections/vyos/vyos/vyos_bgp_global_module.html), [BGP AF](https://docs.ansible.com/projects/ansible/latest/collections/vyos/vyos/vyos_bgp_address_family_module.html), [OSPF interfaces](https://docs.ansible.com/projects/ansible/latest/collections/vyos/vyos/vyos_ospf_interfaces_module.html).\n- NAPALM’s README says VyOS has no HTTP API, contradicted by both stable-release docs; its parsers are stale demand signals, not current authorities. [README](https://github.com/napalm-automation-community/napalm-vyos/blob/develop/README.md), [1.5 API](https://docs.vyos.io/en/1.5/automation/vyos-api.html).\n\n### Remaining unknowns\n\n1. Exact `cli-shell-api`/`config-mgmt` behavior for every immutable 1.4.x and 1.5.x point-release image; inspected GitHub branch tips are mutable.\n2. Concurrent configuration-session conflict behavior; no supported locking contract was found.\n3. Stable machine-readable operational output for interfaces, routes, BGP, OSPF, DHCP, WireGuard, or IPsec; official domain docs primarily show text.\n4. Secret masking for every node in raw `show configuration json`; assume sensitive until verified.\n5. Whether all ordinary domain commits reload, restart, or reset their daemon/session; configuration docs generally do not state this.\n6. Sagitta syslog TLS `host` versus `remote` syntax, which is internally inconsistent in its documentation. [1.4 syslog](https://docs.vyos.io/en/1.4/configuration/system/syslog.html).\n7. Global atomicity boundaries for a mixed-component SSH commit. Circinus API docs explicitly warn that lists spanning components may partially commit, but do not enumerate every component boundary. [1.5 API](https://docs.vyos.io/en/1.5/automation/vyos-api.html#configure).\n\nThose unknowns affect compatibility claims and destructive workflows, but they do not block the recommended first-wave facts and scoped operations."
